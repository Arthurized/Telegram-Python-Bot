FAQ

Frequently asked questions

Grouped by subject. Every answer is self-contained, and every code sample runs as written on Python 3.9 or newer unless it says otherwise.

Basics

What data types are there in Python?
Basics

Everything in Python is an object, and every object has a type you can ask for with type(x). The ones you will actually meet divide into five groups:

Numbers. int (unbounded whole numbers — no overflow, they grow until you run out of memory), float (64-bit binary floating point), complex, and bool, which is technically a subclass of int where True == 1.

Sequences. str for text, list for an ordered mutable collection, tuple for an ordered immutable one, range for an arithmetic sequence computed as you walk it, and bytes/bytearray for raw binary data.

Mappings and sets. dict maps keys to values; set and frozenset hold unique unordered elements.

None. NoneType has exactly one value, None, which means "no value here." It is not zero and not an empty string.

Callables and classes. Functions, classes, methods and modules are all ordinary objects too — you can put a function in a list or pass a class as an argument.

Python prompt
>>> type(42), type(3.14), type("text")
(<class 'int'>, <class 'float'>, <class 'str'>)
>>> type([1, 2]), type((1, 2)), type({1, 2})
(<class 'list'>, <class 'tuple'>, <class 'set'>)
>>> 10 ** 50  # ints have no upper limit
100000000000000000000000000000000000000000000000000

The reference page carries the full table, with mutability and ordering for each type.

What does mutable and immutable actually mean?
Basics

A mutable object can be changed after it is created. An immutable one cannot — operations that look like changes actually build a new object. This matters because assignment in Python never copies: two names can refer to the same object.

Mutable: both names see the change
>>> a = [1, 2]
>>> b = a            # not a copy; the same list
>>> a.append(3)
>>> b
[1, 2, 3]
Immutable: rebinding leaves the original alone
>>> s = "ab"
>>> t = s
>>> s += "c"        # builds a new string, rebinds s
>>> t
'ab'

Immutable: int, float, bool, str, bytes, tuple, frozenset, None. Mutable: list, dict, set, bytearray, and almost every class you write.

Two practical consequences. Only immutable objects can be dictionary keys or set members, which is why you can use a tuple as a key but not a list. And if you need an independent copy of a mutable object, ask for one explicitly: b = a.copy(), or copy.deepcopy(a) when it contains other mutable objects.

Should I use a list, a tuple, or a set?
Basics

Pick by what the collection means, not by which is fastest:

List — a sequence of things of the same kind, where order matters and the contents will change. A list of users, a list of lines from a file. This is the default choice.

Tuple — a fixed group of things whose positions mean different things, like a coordinate (x, y) or a database row. The immutability is the point: it signals "this is one composite value, not a collection you will edit." If you find yourself indexing a tuple past [1], consider a NamedTuple or a dataclass so the fields have names.

Set — when you only care about membership and uniqueness, and never about order. Checking x in collection is roughly constant-time on a set and linear on a list, which turns a slow loop into a fast one on sizeable data.

The membership difference
names_list = ["ada", "grace", "alan"]
names_set  = {"ada", "grace", "alan"}

"alan" in names_list   # scans until found  — O(n)
"alan" in names_set    # hashes and looks up — O(1)

# sets also do algebra
{1, 2, 3} & {2, 3, 4}      # {2, 3}   intersection
{1, 2, 3} | {3, 4}         # {1, 2, 3, 4}  union
{1, 2, 3} - {2}            # {1, 3}   difference
Is Python interpreted or compiled?
Basics

Both, and the question is slightly malformed — "interpreted" and "compiled" describe implementations, not languages.

What CPython, the standard implementation, actually does: it compiles your source to bytecode, a compact instruction set for a virtual machine, and then interprets that bytecode. The compile step is why you see __pycache__ directories appear with .pyc files in them — those are cached bytecode, so unchanged modules do not need recompiling.

There is no separate build command because the compile happens automatically on import. You can watch it:

Looking at the bytecode
>>> import dis
>>> dis.dis(lambda x: x * 2 + 1)
  LOAD_FAST                x
  LOAD_CONST               2
  BINARY_OP                5 (*)
  LOAD_CONST               1
  BINARY_OP                0 (+)
  RETURN_VALUE

Since 3.13 there is also an experimental just-in-time compiler that can turn hot bytecode into machine code at runtime, which blurs the distinction further. Other implementations make different choices entirely: PyPy is a JIT-compiling interpreter, and tools like Cython compile a Python-like language ahead of time to C.

What is PEP 8, and do I have to follow it?
Basics

PEP 8 is the style guide for Python code: four spaces per indent level, snake_case for functions and variables, CapWords for classes, UPPER_CASE for constants, a line-length limit, and rules for where blank lines and spaces go.

Nothing enforces it — code that ignores it runs perfectly. In practice essentially every Python project follows it, which is worth more than any individual rule in it: you can drop into unfamiliar Python and the shapes are already familiar.

You should not apply it by hand. Use a formatter and a linter and stop thinking about it:

Shell
# one tool that formats and lints, now the common choice
python -m pip install ruff
ruff format .          # rewrite the files
ruff check .           # report problems

The guide itself says that consistency within a project beats consistency with the guide, and that readability is the reason for all of it. If a rule makes a particular piece of code harder to read, PEP 8 explicitly tells you to break the rule.

Strings

How do I remove the newline characters at the end of a string?
Strings

Use str.rstrip() with the characters you want gone. Passing "\r\n" strips any trailing combination of carriage returns and newlines while leaving trailing spaces and tabs intact, which is usually what you want when reading a file:

Python prompt
>>> "data\r\n".rstrip("\r\n")
'data'
>>> "  padded  \n".rstrip("\r\n")   # spaces survive
'  padded  '
>>> "a\nb\n\n\n".rstrip("\r\n")    # inner newline survives
'a\nb'

Note that the argument is a set of characters, not a suffix to match. rstrip("\r\n") removes any number of \r and \n in any order. If you want to remove exactly one trailing newline and nothing more, use removesuffix(), added in Python 3.9:

Python prompt
>>> "a\n\n".removesuffix("\n")      # exactly one
'a\n'
>>> "no newline".removesuffix("\n")  # unchanged, no error
'no newline'

The related tools: strip() does both ends, lstrip() the left, and calling any of them with no argument removes all whitespace. When you are splitting a whole document into lines, splitlines() handles the line endings for you and copes with \r\n, \n and \r alike — prefer it over split("\n").

Usually unnecessary

Iterating a text file in the default mode already translates line endings, and most parsers (csv, json) do not care about trailing whitespace. Reach for rstrip when you are handling the text yourself.

How should I format strings?
Strings

Use f-strings. They have been available since Python 3.6 and there is no longer a good reason to use anything else for new code:

f-strings
name = "Ada"
items = 3
total = 21.5

print(f"{name} bought {items} items for {total}")

# the colon introduces a format spec
f"{total:.2f}"        # '21.50'   two decimal places
f"{items:>5}"         # '    3'   right-aligned in 5 columns
f"{1234567:,}"       # '1,234,567'  thousands separators
f"{0.0847:.1%}"      # '8.5%'    as a percentage

# = prints the expression as well as its value: good for debugging
f"{total / items=}"   # 'total / items=7.166666666666667'

The older forms you will still see in existing code: "{} items".format(n), which is fine but more verbose, and "%d items" % n, the C-style operator that predates both. Keep the old style in two places: logging calls, where logging.info("got %s", value) defers the formatting until the message is actually emitted, and anywhere the template comes from outside your program.

Never f-string an SQL query

Interpolating user input into SQL is how injection vulnerabilities happen. Pass parameters to the database driver instead: cur.execute("SELECT * FROM t WHERE id = ?", (user_id,)). The same caution applies to shell commands — pass subprocess a list of arguments rather than a built-up string.

The reference page lists the format specifiers in full.

What is the difference between str and bytes?
Strings

str is text: a sequence of Unicode characters, suitable for anything a human reads. bytes is raw data: a sequence of integers from 0 to 255, suitable for anything a machine reads — file contents, network packets, image data.

Separating the two was one of the central changes in Python 3, and it is why they never mix implicitly. To cross between them you must name an encoding, because there is no universally correct default:

Encoding and decoding
>>> "café".encode("utf-8")       # str  -> bytes
b'caf\xc3\xa9'
>>> len("café"), len("café".encode("utf-8"))
(4, 5)                          # 4 characters, 5 bytes
>>> b"caf\xc3\xa9".decode("utf-8")  # bytes -> str
'café'
>>> "text" + b"bytes"
TypeError: can only concatenate str (not "bytes") to str

In practice: open files in text mode ("r") with encoding="utf-8" stated explicitly when you want text, and binary mode ("rb") when you want bytes. HTTP responses, subprocess output and sockets all hand you bytes, and the decision about how to interpret them is yours.

Always name the encoding
# good: behaves the same on every machine
with open("notes.txt", encoding="utf-8") as f:
    text = f.read()

# risky: uses the platform default, which differs across machines
with open("notes.txt") as f:
    text = f.read()
Why can't I add a number to a string?
Strings
Python prompt
>>> "Total: " + 5
TypeError: can only concatenate str (not "int") to str

Because + would have to guess whether you meant arithmetic or concatenation, and Python refuses to guess — this is "explicit is better than implicit" in action. Languages that do guess give you "Total: 5" in one place and "15" in another from the same operator, and the resulting bugs are genuinely hard to find.

Say which one you want:

Three ways, in order of preference
n = 5

f"Total: {n}"          # 'Total: 5'  — use this
"Total: " + str(n)      # 'Total: 5'  — fine, clunkier
print("Total:", n)       # 'Total: 5'  — print joins with a space

The mirror image catches people reading input: input() always returns a string, so input("age? ") + 1 fails and int(input("age? ")) + 1 works. Wrap that int() in a try if a human is typing.

Functions

How do I use strings to call functions or methods?
Functions

Build a dictionary that maps each string to a function object. Functions are ordinary values in Python, so they can sit in a dictionary like anything else. The great advantage of a lookup table is that the strings do not have to match the function names, and nothing outside the table can be reached:

Dispatch table
def start_engine():
    print("starting")

def stop_engine():
    print("stopping")

# note: no parentheses — we store the functions, not their results
actions = {
    "go":   start_engine,
    "stop": stop_engine,
}

command = input("command: ")
action = actions.get(command)

if action is None:
    print(f"unknown command: {command!r}")
else:
    action()

For methods on an object, getattr is the direct equivalent, but it will reach anything on the object, so restrict it:

getattr, carefully
ALLOWED = {"upper", "lower", "title"}

def apply(text, method_name):
    if method_name not in ALLOWED:
        raise ValueError(f"not permitted: {method_name}")
    return getattr(text, method_name)()

apply("hello", "upper")   # 'HELLO'
Not with eval

eval(user_string) and exec(user_string) will also work, and will run anything at all that the string contains — including code that deletes files. If the string came from outside your program, treat both as off limits. A dispatch dictionary is faster, clearer and cannot be abused.

How do I create higher-order functions?
Functions

A higher-order function takes functions as arguments, returns a function, or both. The simplest way to return one is to define it inside another function. The inner function keeps access to the outer function's variables, which makes it a closure:

Returning a function
def linear(a, b):
    """Return the function x -> a*x + b."""
    def apply(x):
        return a * x + b     # a and b stay available
    return apply

double_plus_one = linear(2, 1)
double_plus_one(10)              # 21

# each call captures its own a and b
negate = linear(-1, 0)
negate(10)                      # -10

Taking a function as an argument needs no special syntax at all — just call the parameter:

Accepting a function
def apply_twice(fn, value):
    return fn(fn(value))

apply_twice(str.upper, "ab")      # 'AB'
apply_twice(lambda n: n * 3, 2)   # 18

# the built-ins that take functions
words = ["pear", "fig", "banana"]
sorted(words, key=len)            # ['fig', 'pear', 'banana']
max(words, key=len)               # 'banana'

Two tools from functools are worth knowing. partial fixes some arguments of an existing function, which is often tidier than writing a closure by hand; cache memoises results:

functools
from functools import partial, cache

int("1101", 2)                     # 13
from_binary = partial(int, base=2)
from_binary("1101")                  # 13

@cache                             # remembers past results
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

fib(100)                           # instant; without @cache, hopeless
Why does my function remember the previous call's list?
Functions

Because default argument values are evaluated once, when the def statement runs — not on each call. A mutable default is therefore shared by every call that does not override it. This is the single most common surprise in the language:

The trap
def add_item(item, basket=[]):     # don't do this
    basket.append(item)
    return basket

add_item("apple")                   # ['apple']
add_item("pear")                    # ['apple', 'pear']  ← surprise
add_item("fig")                     # ['apple', 'pear', 'fig']

The fix is to default to None and build a fresh object inside the function:

The fix
def add_item(item, basket=None):
    if basket is None:
        basket = []                  # new list on every call
    basket.append(item)
    return basket

Immutable defaults — numbers, strings, None, tuples — are perfectly safe, because nothing can modify them. The rule is simply: never use [], {}, set(), or an instance of your own class as a default value.

The same evaluate-once behaviour bites with any expression: def log(when=datetime.now()): records the time the module was imported, forever.

What are *args and **kwargs?
Functions

They let a function accept any number of arguments. *args collects extra positional arguments into a tuple; **kwargs collects extra keyword arguments into a dictionary. The asterisks are the syntax; the names are only convention.

Collecting
def describe(label, *values, **options):
    print(label, values, options)

describe("nums", 1, 2, 3, reverse=True)
# nums (1, 2, 3) {'reverse': True}

The same symbols work in reverse at the call site, unpacking a sequence or a mapping into arguments:

Unpacking
point = (3, 4)
settings = {"sep": " | ", "end": "!\n"}

print(*point, **settings)      # 3 | 4!
# identical to: print(3, 4, sep=" | ", end="!\n")

The main use is writing a wrapper that must pass everything through without knowing the signature it is wrapping — which is exactly what decorators do. A bare * in a signature is a related trick: it forces every parameter after it to be passed by name, which makes call sites much easier to read.

Keyword-only parameters
def connect(host, *, port=443, verify=True):
    ...

connect("example.com", port=8080)   # fine
connect("example.com", 8080)        # TypeError — and that's the point
What is a decorator?
Functions

A decorator is a function that takes a function and returns a replacement for it. The @ syntax is shorthand:

The @ is only sugar
@timed
def work():
    ...

# means exactly this:
def work():
    ...
work = timed(work)

So a decorator is useful whenever you want to wrap behaviour around a function without editing its body — timing, logging, caching, retries, access checks. Here is a complete one:

A decorator that times calls
import functools
import time

def timed(fn):
    @functools.wraps(fn)            # keep fn's name and docstring
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        try:
            return fn(*args, **kwargs)
        finally:                    # report even if it raised
            elapsed = time.perf_counter() - start
            print(f"{fn.__name__} took {elapsed:.3f}s")
    return wrapper

@timed
def slow_add(a, b):
    time.sleep(0.2)
    return a + b

slow_add(1, 2)                   # prints: slow_add took 0.200s

Two details that matter. functools.wraps copies the original function's name, docstring and annotations onto the wrapper — without it, your function is called wrapper in every traceback and help page. And *args, **kwargs means the wrapper works on any signature.

You will meet plenty of decorators before you write one: @property, @staticmethod, @classmethod, @dataclass, @functools.cache, and the route decorators in every web framework.

Data structures

What is a comprehension, and when should I not use one?
Data

A comprehension builds a collection from an iterable in a single expression. It is the most characteristic construct in the language:

The four forms
nums = [1, 2, 3, 4, 5]

[n * n for n in nums]                  # list  [1, 4, 9, 16, 25]
{n % 3 for n in nums}                  # set   {0, 1, 2}
{n: n * n for n in nums}              # dict  {1: 1, 2: 4, ...}
(n * n for n in nums)                  # generator — lazy

# with a filter
[n for n in nums if n % 2 == 0]         # [2, 4]

# equivalent loop, for comparison
squares = []
for n in nums:
    squares.append(n * n)

Prefer a comprehension when you are building a collection by transforming or filtering another one, and the whole thing fits comfortably on one line. Use a loop instead when:

It needs two conditions and a nested loop. If you have to read it twice, it has stopped being clearer than the loop.

The body has side effects. A comprehension written for its side effect, whose list you then throw away, is a loop wearing a disguise. Write the loop.

The result is enormous. A list comprehension materialises every element. Use a generator expression — round brackets — to stream instead, which matters for files and large query results:

Generator: constant memory
# reads the whole file into memory
total = sum([len(line) for line in open("big.log")])

# reads one line at a time
total = sum(len(line) for line in open("big.log"))
Are dictionaries ordered?
Data

Yes. Since Python 3.7 a dict is guaranteed to preserve insertion order, and iterating it gives you keys in the order they were first added. In 3.6 this was already true but was an implementation detail you were told not to rely on; in 3.7 it became a language guarantee.

Python prompt
>>> d = {"z": 1, "a": 2, "m": 3}
>>> list(d)
['z', 'a', 'm']                  # insertion order, not sorted
>>> d["z"] = 99                 # updating keeps the position
>>> list(d)
['z', 'a', 'm']

Two caveats. Ordered is not sorted — if you want alphabetical, ask for it: sorted(d.items()). And set is still unordered; iteration order there is an accident of hashing and must never be relied on.

collections.OrderedDict still exists and is still occasionally useful, because it compares order-sensitively (OrderedDict([("a",1),("b",2)]) != OrderedDict([("b",2),("a",1)]), whereas the equivalent plain dicts are equal) and has a move_to_end() method. For simply keeping insertion order, a plain dict is enough.

What is the difference between is and ==?
Data

== asks whether two objects have the same value. is asks whether two names refer to the very same object in memory. You almost always want ==.

Python prompt
>>> a = [1, 2, 3]
>>> b = [1, 2, 3]
>>> a == b          # same contents
True
>>> a is b          # two separate lists
False
>>> c = a
>>> c is a          # the same list
True

Use is only for the three singletons, where there is exactly one instance in the whole interpreter: x is None, x is True, x is False. is None is the idiomatic null check.

Why is sometimes seems to work

CPython caches small integers and short strings, so 256 is 256 is True while 1000 is 1000 may not be. This is an optimisation, not a promise, and it differs between versions and implementations. Code that relies on it is broken code that happens to pass today. Modern Python will warn you with a SyntaxWarning when you compare a literal with is.

Running Python

What is the advantage of Python's libraries?
Runtime

Two separate advantages that get conflated: the standard library, which is already installed, and the package index, which is not.

The standard library is unusually broad — the phrase used about it is "batteries included." It ships with facilities for internet protocols and formats: modules for writing HTTP servers and clients, parsing and composing e-mail, reading and writing XML, JSON and CSV. It also wraps the operating system in a portable way, so the same script handles paths, processes and files on Windows, macOS and Linux without changes. Useful programs frequently need nothing beyond it:

A sample of what is already installed
NeedModule
Paths and the filesystempathlib, os, shutil, glob
Structured data filesjson, csv, sqlite3, tomllib
Web requests and serversurllib.request, http.server
Dates and timesdatetime, zoneinfo, calendar
Command-line interfacesargparse, sys, getpass
Running other programssubprocess, shlex
Concurrencyasyncio, threading, multiprocessing
Testing and debuggingunittest, pdb, logging, dis
Text and binary wranglingre, textwrap, struct, difflib
Maths and randomnessmath, statistics, random, secrets
Archives and compressionzipfile, tarfile, gzip
Better data structurescollections, itertools, dataclasses

The Python Package Index adds several hundred thousand third-party projects, installable with one command. Its real significance is the depth in particular fields: for numerical and scientific work, machine learning, and data analysis, the Python packages are not merely available but are the tools the field actually uses, which means the examples, the papers, the tutorials and the job adverts all assume them.

Worth knowing about the trade-off, though. Anything you install is code from a stranger, running with your privileges. Check what you are adding, pin your versions, and prefer the standard library when it will do — the module index is the first place to look, not the last.

What is a virtual environment, and do I need one?
Runtime

A virtual environment is a private directory holding its own copy of the interpreter's package directory. Packages installed while it is active go there instead of into the system Python. Yes, you need one — one per project, always.

Without them, every project on the machine shares one set of packages. The first time two projects need different versions of the same library, you have an unsolvable problem.

The whole workflow
# create it, once per project
python -m venv .venv

# activate it, once per terminal session
source .venv/bin/activate      # macOS and Linux
.venv\Scripts\activate         # Windows

# now pip installs into the project, not the system
python -m pip install requests

# record what you installed, so others can reproduce it
python -m pip freeze > requirements.txt
python -m pip install -r requirements.txt

deactivate                     # when you are done

Add .venv/ to your .gitignore. The environment is disposable and machine-specific; the requirements.txt is the thing worth committing.

Two conveniences. Writing python -m pip rather than pip guarantees you are installing into the interpreter you think you are, which eliminates a whole genre of confusion. And newer tools — uv and Poetry among them — manage the environment and the dependency list together; they are worth a look once the manual version makes sense to you.

What is the GIL, and has it been removed?
Runtime

The Global Interpreter Lock is a mutex inside CPython that allows only one thread to execute Python bytecode at a time. Its consequence: threads in Python have historically given you no speed-up on CPU-bound work, no matter how many cores the machine has.

It exists because it makes the interpreter's memory management simple and single-threaded code fast. Removing it had been proposed repeatedly for twenty years and rejected each time, because every attempt slowed down the single-threaded case that nearly all Python actually is.

The current state. Python 3.13 shipped an experimental separate build in which the lock can be disabled, and in 3.14 that free-threaded build became officially supported. So the honest answer is: it is optional now, in a build you have to choose deliberately, and the default interpreter most people run still has it. Packages with C extensions need their own work to be safe without it, so the ecosystem is still catching up.

What to do today. Choose by the kind of work, which is the right habit regardless of what happens to the lock:

Picking a concurrency model
WorkUseWhy
Waiting on network or disk asyncio Thousands of waits, one thread, no lock contention
A few blocking calls threading The lock is released during I/O, so threads do help here
Heavy computation multiprocessing Separate processes, separate interpreters, real cores
Numeric arrays numpy and friends The loop runs in C, which drops the lock anyway
Why is Python slow, and when is it not?
Runtime

Pure Python arithmetic is slow for structural reasons. Every value is a heap-allocated object, so a + b means looking up both objects' types and dispatching to the right addition; names are resolved in dictionaries at runtime rather than being fixed offsets; and nothing can be specialised ahead of time, because any name might be rebound to a different type at any moment. A tight numeric loop can run one to two orders of magnitude slower than the equivalent C.

It is not slow when the work is not happening in Python. This is the key insight, and it is why the performance question matters far less in practice than it sounds:

Same result, very different cost
# a million Python-level operations
total = 0
for x in data:
    total += x * 2

# one Python-level call; the loop runs in C
import numpy as np
total = (np.asarray(data) * 2).sum()

So the real rule is to keep the loops out of Python. Hand bulk work to a library that loops in C, and let Python be the thing that decides what to do rather than the thing that does it.

Beyond that, in rough order of how much they pay back: measure before you optimise (cProfile, or timeit for small pieces) — the slow part is routinely not where you guess; fix the algorithm, since the right data structure beats any micro-optimisation; cache repeated work with functools.cache; and only then consider PyPy, Cython, or writing the hot part in Rust or C. Note also that the interpreter itself has got substantially faster since 3.11, so upgrading is sometimes the entire fix.

And the usual caveat: most programs are not CPU-bound at all. If yours spends its time waiting for a database, a network call or a disk, the interpreter's speed is irrelevant.

Errors and types

How should I handle errors?
Errors

Catch the specific exceptions you can actually do something about, and let everything else propagate. A traceback that stops the program is far more useful than a program that carries on with wrong data.

The full form
try:
    value = int(raw)
except ValueError as err:          # only what you can handle
    print(f"not a number: {err}")
    value = 0
else:
    print("parsed cleanly")          # ran only if no exception
finally:
    print("always runs")            # cleanup, even on raise

Do not write a bare except:. It catches KeyboardInterrupt and SystemExit too, so your program becomes unkillable and silently swallows bugs. If you genuinely need a catch-all — at the top of a long-running server, say — catch Exception and log it with its traceback:

Catch-all, done properly
import logging

try:
    handle_request()
except Exception:
    logging.exception("request failed")   # logs the traceback
    # carry on serving the next request

Python's style is to try the operation and handle the failure, rather than checking first — "easier to ask forgiveness than permission." Checking first is also a race condition: a file can vanish between your check and your open.

Idiomatic, and also correct
# preferred
try:
    with open(path, encoding="utf-8") as f:
        data = f.read()
except FileNotFoundError:
    data = ""

# racy: the file may be deleted after the check
if os.path.exists(path):
    ...

Use with for anything that must be closed; it releases the resource even if the block raises. Raise built-in exceptions where they fit — ValueError for a bad value, TypeError for a bad type, KeyError for a missing key — and define your own by subclassing Exception when callers need to distinguish your failures from everyone else's. The exception hierarchy is on the reference page.

Do type hints do anything at runtime?
Types

No. Python does not check them and does not enforce them. This runs without complaint:

Hints are not checks
def greet(name: str) -> str:
    return f"hello {name}"

greet(42)        # 'hello 42' — runs fine, no error

Hints are for tools and for readers. Their value comes from running a type checker, as a separate step, which finds the mistake before the program does:

Shell
python -m pip install mypy
mypy app.py
app.py:5: error: Argument 1 to "greet" has incompatible
type "int"; expected "str"

The notation you need for most code:

Common annotations
names: list[str]                 # list of strings
scores: dict[str, int]           # str keys, int values
maybe: str | None                # str or None (3.10+)
pair: tuple[int, int]            # exactly two ints

def total(values: list[float]) -> float:
    return sum(values)

Worth hinting function signatures in anything you expect to keep, since that is where the information helps most — your editor will autocomplete and catch typos. Not worth annotating every local variable. And because the checker is optional, hints can be wrong: they describe intent, and only a checker in your workflow keeps them honest.

One runtime exception to the rule: some libraries do read annotations deliberately. Pydantic validates against them and FastAPI builds request parsing from them, so in those frameworks the hints really are load-bearing.

What is the operator precedence in Python?
Reference

From tightest binding to loosest, the groups are: parentheses and displays; attribute access, subscription and calls; await; **; unary +x -x ~x; * @ / // %; + -; << >>; &; ^; |; all the comparisons together with in and is; not; and; or; the conditional expression; lambda; and finally :=, which binds loosest of all.

The reference page has the complete table with associativity. In practice, four things are worth committing to memory:

The ones that actually catch people
-2 ** 2              # -4, not 4 — ** binds tighter than unary minus
2 ** 3 ** 2          # 512, not 64 — ** is right-associative
not a == b            # not (a == b) — comparison binds tighter
1 < x < 10            # chains, meaning (1 < x) and (x < 10)

# and the classic bitwise-vs-comparison trap
mask & 1 == 0          # mask & (1 == 0)  — almost never what you meant
(mask & 1) == 0        # write the parentheses

The practical advice is that nobody should have to consult this table to read your code. Where an expression mixes arithmetic with bitwise or comparison operators, add parentheses even when they are redundant.
