History

The history of Python

Python was started by one person over a Christmas break in 1989. Thirty-five years later it is the most-used language on GitHub. This is how that happened.

01 Timeline

Timeline

  1. 1980s

    A teaching language called ABC

    Guido van Rossum worked at CWI1 in Amsterdam on ABC, a language for teaching people who were not programmers. He liked that readable layout was enforced rather than suggested, and was frustrated that ABC could not be extended or reach the operating system underneath. Those frustrations became a list of requirements.

  2. Dec 1989

    Written over a Christmas break

    With the CWI offices shut for the holidays, van Rossum started an interpreter for the language he had been sketching. He named it after Monty Python's Flying Circus, wanting something short and slightly irreverent. The snake came later, and only because of the name.

  3. Feb 1991

    Version 0.9.0, posted to a newsgroup

    The first public release went out by hand to alt.sources, split across nine posts because of message size limits. It already had functions, modules, exceptions, classes with inheritance, and the core types. Read it today and the syntax is almost entirely familiar.

  4. Jan 1994

    Version 1.0

    Added lambda, map(), filter() and reduce(), contributed by users who missed functional programming. Python has been ambivalent about all four ever since; reduce() was moved out of the built-ins in Python 3.

  5. Oct 2000

    2.0 — list comprehensions and Unicode

    List comprehensions arrived, borrowed from Haskell, and became the most characteristically Python construct there is. Unicode support landed, as did a garbage collector that could collect reference cycles. The PEP process was formalised the same year, and the Python Software Foundation followed in 2001 to hold the licence and the intellectual property.

  6. Dec 2008

    3.0 — breaking compatibility on purpose

    A deliberate, one-time break to fix accumulated design mistakes. print became a function; text and binary data were separated into str and bytes, with str Unicode by default; / started doing true division.

    It was the right set of changes and a painful decade of migration, and it is now the cautionary tale cited whenever a language proposes a major version bump. Python 2.7, released in 2010, was the last of the old line.

  7. 2014–16

    pip, async and f-strings

    Three releases that shaped how Python is written now. 3.4 bundled pip, so installing packages stopped being a tutorial's first obstacle. 3.5 gave asynchronous code real syntax with async and await, and defined a standard notation for type hints. 3.6 introduced f-strings.

  8. Jul 2018

    Guido van Rossum steps down

    After a bruising public argument over the assignment expression :=, van Rossum resigned as Benevolent Dictator For Life, citing the tone of the debate, and deliberately named no successor. Core developers voted for an elected five-person Steering Council, which took office in February 2019.

  9. Jan 2020

    Python 2 reaches end of life

    Support formally ended on 1 January 2020, with a final tidying-up release in April. Twelve years after 3.0 shipped, the split was over.

  10. Oct 2021

    3.10 — structural pattern matching

    match/case is considerably more than a switch statement, because it destructures. Less glamorous and more useful day to day: error messages were rewritten to say what was actually wrong and point at the right character.

  11. Oct 2022

    3.11 — a faster interpreter

    The first release of the Faster CPython effort, benchmarking roughly 1.25× faster than 3.10 overall. Tracebacks began pointing at the exact expression that failed rather than just the line.

  12. Oct 2024

    3.13 — the lock becomes optional

    An experimental build shipped in which the global interpreter lock can be switched off, making genuine multi-core threading possible in pure Python for the first time. An experimental just-in-time compiler arrived alongside it.

  13. Oct 2025

    3.14 — free-threading supported

    The free-threaded build moved from experimental to officially supported, which is the real milestone: something you can plan a project around rather than an experiment to watch.

  14. Oct 2026

    3.15

    Due on the annual cadence. This page was written from information available in mid-2026, so check the official version table for what is current and what is still supported.

A common mix-up

Python 3000, or Py3k, was never a released version. It was the long-running codename for the cleanup release that eventually shipped as 3.0 in December 2008 — the "3000" was a joke about how far off it was. The first released version was 0.9.0, in February 1991.

  1. CWI is the Centrum Wiskunde & Informatica, the Dutch national research institute for mathematics and computer science, in Amsterdam. It is also where the Python interpreter was first written. Back to the text
02 Design

PEP 20

The Zen of Python

In 1999 the core developer Tim Peters wrote down the aesthetic principles he thought the language was built on. They were published as PEP 20 and planted inside Python itself as an easter egg: type import this at any prompt to read all nineteen. Three of them do most of the real work.

  • “Explicit is better than implicit.” Python would rather make you write the step out than guess what you meant. It is why there is no implicit coercion between strings and numbers, and why self is an ordinary visible parameter.
  • “Readability counts.” The justification for the most divisive feature in the language: indentation is syntax. You cannot write Python whose layout lies about its structure, because the layout is the structure.
  • “Errors should never pass silently.” Python raises rather than returning a quiet null you might not check. A program that stops loudly beats one that carries on with nonsense in a variable.

Peters wrote nineteen and left the twentieth to van Rossum, who never filled it in; the joke is that the list will never be finished. Read them in full in PEP 20.

03 Governance

How Python is governed

Python has no owning company, and nobody can simply decide to add a feature.

Every significant change goes through a Python Enhancement Proposal: a numbered design document stating what is proposed, why, which alternatives were rejected, and how backwards compatibility will be handled. Anyone may write one. A proposal moves from draft through public discussion to accepted or rejected, and becomes final once it ships. Rejected PEPs are kept and published, which makes the index an unusually honest archive — you can read exactly why some much-requested feature is not in the language.

Worth reading once

The PEP index is the primary source for every claim on this page. If Python does something that looks strange, searching the PEPs almost always turns up a document explaining why, and naming the alternatives that lost.
